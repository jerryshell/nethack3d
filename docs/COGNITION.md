# 认知文档

本文件记录项目的当前认知：目标、决策、进度、风险与下一步。
架构细节见 `docs/DESIGN.md`，使用方式见 `README.md`。
每个里程碑完成后更新本文件。

## 项目目标

在浏览器中实现三维 NetHack，满足以下约束：

- 参考实现为本地 NetHack 5.0 C 源码，数据由脚本提取，不凭记忆编写。
- 技术栈为 Bun、TypeScript、Vite 与 three.js，静态检查使用 oxlint 与 oxfmt。
- 玩法为回合制 roguelike：地牢生成、战斗、物品、鉴定、饥饿、角色创建与存档。
- 界面支持英文与简体中文，运行时切换。
- 关键路径有日志，便于日后排查。
- 文档与注释使用简体中文。

## 关键决策

| 决策                                             | 理由                                   |
| ------------------------------------------------ | -------------------------------------- |
| 数据从 C 头文件提取并生成带类型的模块            | 数据可核对、可复现，构建不依赖参考源码 |
| 关卡由 `(seed, depth)` 确定性生成                | 存档只需保存种子，体积小且稳定         |
| 游戏逻辑与语言解耦，消息只存键与 ID              | 切换语言后历史消息也能重新翻译         |
| 全部模型程序化生成                               | 仓库自包含，无美术资源与版权问题       |
| 随机数沿用 NetHack 语义                          | 便于与原版概率对照，行为可预期         |
| 严格模式 TypeScript，`tsc --noEmit` 作为提交门槛 | 类型即文档，减少运行时错误             |
| 日志默认只输出 warn 与 error                     | 避免刷屏，需要时用 `?debug=1` 打开     |

## 参考事实

以下结论已通过阅读源码或运行脚本确认：

- `include/monsters.h` 有 394 条 `MON(` 条目，条目格式为
  `MON(NAM/NAMS(...), S_*, LVL(等级,速度,护甲,魔抗,阵营), (G_*|频率), A(ATTK(...)×6), SIZ(...), MR1, MR2, M1.., M2.., M3.., 难度, CLR_*, TAG)`。
- 护甲字段的含义是 `10 - 加成`，例如板甲 `ac = 3` 对应 7 点防护。
- 法术书等级存放在 `OBJECT` 的第 12 个参数，未鉴定外观在类别内洗牌决定。
- 命中公式位于 `uhitm.c` 的 `find_roll_to_hit()` 与 `mhitu.c`；
  负护甲通过 `AC_VALUE` 随机化并减免伤害，而不是免疫攻击。
- 怪物难度窗口来自 `include/monst.h`：下界 `depth / 6`，上界 `(depth + 玩家等级) / 2`。
- 初始属性使用 `init_attr(75)` 与按职业分布重分配的点数机制。

## Agent 反馈循环

项目内置让 Agent 自行测试与迭代的闭环，详见 `docs/AGENT-LOOP.md`：

- `bun run agent` 运行 10 条确定性场景与模糊测试，并比对快照；
- 不变量覆盖位置、数值、实体唯一性、装备一致性与迷雾单调性；
- 失败时输出复现命令与现场快照（地图 + 状态），产物在 `tools/agent-artifacts`；
- `bun run agent:repl` 提供逐条命令的 JSON 应答，便于交互探查；
- `bun run agent:e2e` 用真实浏览器检查渲染与界面，产出截图。

首轮运行发现两个真实问题：锁门死路（已通过踹门机制修复）与换层后迷雾
基线未重置（已通过追踪器修复）。新增机制时应同步补充不变量与场景。

## 采集到的经验

- 宏替换必须跳过字符串字面量，否则 `FOOD("tin", ..., METAL, ...)` 中的
  `tin` 会被参数值替换，产生错误数据。
- 命名冲突需要留意：自定义的 `clear()` 会覆盖 `THREE.Group.clear()`，改名为 `clearAll()`。
- 视野必须在移动后立即重算，否则渲染使用上一格的可见性。
- 存档往返测试应覆盖属性、背包、装备、迷雾与怪物，任何遗漏都会在继续游戏时暴露。
- 不变量要覆盖「派生视图与状态一致」，只检查「可见瓦片是否被记忆」会漏掉
  视野未重算的情况；加上「玩家所在格必须在视野内」才能捕获该类回归。
- 在本环境里，一个进程内首次调用 git 需要约 10 秒（冷启动），之后约 0.1 秒。
  高频路径应直接解析 `.git/HEAD` 与文件散列，避免子进程。
- 报告类输出要先补齐派生字段再落盘，否则终端显示正常而产物缺字段。
- 锁门等「只进不出」的关卡结构需要专门的通过手段，否则会出现无法继续的死局；
  反馈循环首轮就发现了这一点。
- 本机存在进程首次启动的异常开销：`git` 约 10 秒，`bun --bun vite` 比普通
  `vite` 慢约 8 倍（23 秒对 3 秒），浏览器首次启动约 72 秒。
  照搬文档里的推荐命令前先测一次，慢就换回普通调用。
- 浏览器端到端检查的耗时几乎全在启动浏览器，页面打开一步就占 72 秒，
  其余 11 项合计不足 5 秒。固定会话名并复用可降到约 9 秒。
- `bun:test` 启动约 0.2 秒，内置覆盖率能直接列出未覆盖行号；
  覆盖率门槛按全局百分比判定，取值需在 0 到 1 之间，超过 1 会直接判失败。
- Bun 原生接口可直接替换 Node：`Bun.write` 自动创建父目录，
  `Bun.CryptoHasher` 与 `node:crypto` 结果一致，`import.meta.dir` 取代
  `fileURLToPath(import.meta.url)`。
- 先测量再改配置。Vite 侧实测三项均无收益：`build.target` 取 es2022、
  esnext 与默认值的产物完全一致（859KB，gzip 199KB）；开发服务器就绪 2.1 秒、
  38 个模块抓取不足 80 毫秒，`server.warmup` 只能省约 60 毫秒；
  three.js 已被有效摇树，产物中不含 AudioListener、GLTFLoader 等未用子系统。
- Vite 7 默认客户端压缩器已是 oxc，与项目的 oxlint、oxfmt 同源，无需配置。
- `server.strictPort` 值得打开：默认行为是端口占用时静默改用下一个端口，
  自动化脚本可能连上来源不明的旧服务，实测中真的踩到过一次。
- 自动化脚本必须校验「测的是哪个服务」。残留的服务会让生产产物检查
  悄悄连上开发服务器并全部通过，得到完全错误的结论。
- Windows 上杀子进程要认准真身：套一层 `bun run` 或调用 `node_modules/.bin`
  里的批处理壳，`kill` 只杀得掉包装进程，服务会留在端口上。
  直接运行 `node_modules/vite/bin/vite.js` 才能干净结束。
- 渲染开销要先量再改。实测几何侧压力极小（26 到 43 次绘制、约 1 万个三角面、
  4 个着色器程序），因此优化方向是填充率而非几何：
  低质量档位关掉多重采样并把像素比限制为 1。
- `renderer.shadowMap.enabled` 打开但没有任何灯光设置投影时，整套阴影配置
  是无效代码。要么补上投影，要么删掉，别让它留在配置里误导判断。
- glTF 贴图的 UV 约定是 `flipY = false`，而 `TextureLoader` 默认 `true`。
  混用时 V 坐标会翻转，采样落到图集的空白区域，模型整片发黑且不报错。
- 外部素材要按「可校验、可回退」设计：清单记录散列并纳入 verify，
  加载失败时回退到程序化几何体，避免素材缺失让游戏起不来。
- 视觉问题用截图确认最快。把模型并排渲染到临时页面，比在游戏里逐个寻找
  更快看出朝向、缩放与贴图是否正常。界面改动的截图检查同样必要：
  状态格标签曾整片显示成原始 i18n 键名，测试全绿但肉眼一看就知道不对。
- 界面元素要能点得动才给出来。楼梯未探索时仍显示「前往楼梯」，
  点击毫无反应，比没有这个按钮更让人困惑。
- 复用文案要看清语境。动作菜单直接用了提问式文案，按钮上出现「持握什么？」，
  正确做法是为动作单独准备一组标签。
- 打开面板时要收起挂在光标上的浮层。键盘打开背包后，光标提示仍留在屏幕中间，
  只有截图才能发现这类残留。
- 合成事件会绕过命中测试。`canvas.dispatchEvent(new PointerEvent(...))` 让点击
  检查一路绿灯，而真实鼠标点击全被覆盖层吃掉。自动化交互必须用真实鼠标事件，
  并用 `document.elementFromPoint` 断言该位置的最顶层元素是谁。
- 全屏覆盖层的指针事件要逐元素指定。`#ui > * { pointer-events: auto }` 这类
  按容器写的规则会一次性命中 HUD 与弹窗：HUD 挡住画布，弹窗又被改成穿透。
  正确做法是按具体元素（`#ui > .hud`）提高权重，只让操作区自行开启事件。
- 这类问题的定位顺序：先问「点击点上的最顶层元素是谁」，再看它是否该接收事件，
  比逐行读事件绑定快得多。
- 地图「看起来奇怪」要先量化再改。把生成结果画成 ASCII 并统计异常
  （走廊穿房、贴着房间外墙、门连成排、房间没有门），比盯着效果图猜快得多。
- 全图最短路会把走廊引成贴着房间的小回路。加上「转弯代价」后，
  同样的代价模型就能给出长直线走廊：状态里带上进入方向即可。
- 约束过严会换来断连。禁止走廊贴房间一度让房间连不上（自检立刻报出
  「every room reachable」失败），最后靠「房间间距留 3 格」从源头腾出空间，
  而不是在寻路上硬性拒绝。
- 冒烟脚本要少做「调试式操作」。按两次 Esc 会退回主菜单，后续步骤便跑在
  已停止的会话上；一次跑绿并不说明游戏有问题，先怀疑脚本的假设。
- 断言不要用容错值兜底。`Number(值 ?? -1)` 在字段缺失时反而成立，
  会让检查变成假通过；读不到数字就应当直接判失败。
- 在 `update()` 里加提前返回要格外小心：为玩家动画加的一处 return
  跳过了地牢与相机更新，画面直接全黑，而单元测试全绿。
  这类问题只有看截图才发现。
- 蒙皮网格必须用 `SkeletonUtils.clone` 复制，普通 `Object3D.clone` 不会重绑骨骼。
- 人物模型的贴图要与模型保持相对目录结构，glTF 里的贴图路径相对于模型文件。
- 表驱动的效果比逐类型写分支好维护：陷阱只分十种效果类型，
  新增陷阱类型是加一行数据，不是加一段逻辑。
- 让新机制真正致命之后，既有测试可能变得不稳定：陷阱一上线，
  冒烟测试里就出现「玩家提前阵亡」的偶发失败。测试要对这种路径也成立，
  而不是假设流程一定走到最后一步。
- 结构性判断不要依赖瓦片类型。房间地面会被楼梯、陷阱、设施覆盖，
  按 `tiles[i] === ROOM` 判断房间所在侧会把门朝向判反；房间矩形才是稳定依据。
  但矩形只回答一半：走廊贴着房间外墙经过时，通道走向才是门的真实朝向，
  房间所在侧只能当兜底。
- 用同一份判定核对判定，等于没核对。门朝向就是这么漏掉的：旧断言直接
  用 `doorBlocksEastWest` 的分支对照它自己，永远全绿；换成从 ASCII 地图
  的通道走向独立推导期望值后，48 层样本一次找出 39 扇判反。
- 子节点的坐标是相对父节点的。门板挂在转轴上，转轴又在格子边缘，
  把「半个门板长度」当成绝对坐标写进去，整扇门就偏出半格；
  这类错误只有量出世界坐标才看得清。
- 视觉问题的排查顺序：先量数值（相对偏移、包围盒），再看截图。
  单看暗场截图很容易把「方向对了但位置偏了」误判成方向问题。
- 引用数据里的 id 前先确认它存在。施法职业集合一开始写成 `PRIEST`/`WARRIOR`，
  而抽取出的职业 id 是 `CLERIC`/`BARBARIAN`，结果是牧师拿不到加成、
  测试里的战士直接构造失败。这类错误不报语法问题，只在运行时显形。
- 合成的指针事件没有活动指针，`setPointerCapture` 会抛错；
  自动化测试点击画布时需要容错，否则整条点击链路中断。
