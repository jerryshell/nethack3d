# 参考版本同步

游戏数据由脚本从参考 NetHack 仓库提取，因此必须记录生成时的源码版本。
本页说明记录内容、漂移检测方式与上游更新后的同步流程。

## 记录的版本

记录文件为 `tools/nethack-reference.json`，随仓库提交。

| 字段     | 当前值                                                  |
| -------- | ------------------------------------------------------- |
| 参考仓库 | `git@github.com:NetHack/NetHack.git`                    |
| 仓库路径 | `../nethack`（相对项目根目录，可用 `NETHACK_SRC` 覆盖） |
| 分支     | `NetHack-5.0`                                           |
| 提交     | `c1b1b08e95dc5e5ad55760e20affd45de5dd7e90`              |
| 提交时间 | 2026-09-26 11:47:20 -0400                               |
| 提交标题 | follow-up: timestamp in bones was already relative      |
| 记录条目 | 怪物 394、物品 440                                      |
| 生成数据 | 怪物 394、物品 440、职业 13、种族 5                     |

记录中另存关键文件的 sha256 前 16 位。文件清单与提取脚本实际读取的文件一致：

| 文件                 | 用途                       |
| -------------------- | -------------------------- |
| `include/monsters.h` | 怪物原型与攻击骰           |
| `include/objects.h`  | 物品原型、伤害骰、护甲加值 |
| `include/defsym.h`   | 怪物字形类别               |
| `include/color.h`    | 颜色编号                   |
| `src/role.c`         | 职业与种族数据             |

## 漂移检测

```bash
bun run sync:check          # 有漂移时退出码为 1，可直接用于 CI
bun run sync:check --json   # 机器可读，供 Agent 判断
bun tools/sync-nethack.ts --full-diff   # 查看关键文件的完整补丁
```

检测分三层，任意一层发现变化即视为漂移：

1. **文件散列**：关键文件内容变化，即使参考仓库工作区没有提交也能发现。
2. **条目数量**：参考文件中的 `MON(` 与类宏条目数与记录不符。
3. **生成数据**：`src/data` 的条数与记录时不一致，说明提取脚本尚未重跑。

检出漂移时输出差异统计与相关提交列表，并给出同步步骤。
参考仓库工作区不干净时额外提示，因为此时的记录无法完全代表生成数据。

提取脚本在结束时也会做同样检查：参考文件变化时打印提示，避免生成结果静默过期。

## 上游更新后的同步流程

1. **更新参考仓库**：在参考目录执行拉取，确认落在目标分支。

   ```bash
   git -C ../nethack pull --ff-only
   ```

2. **查看差异**：`bun tools/sync-nethack.ts --full-diff`。
   重点看条目数量变化与攻击、伤害、护甲等数值改动。

3. **重新提取**：`bun run extract`。
   生成文件会更新，同时打印是否仍有漂移。

4. **检查回归**：`bun run agent`。
   若快照不一致，先确认变更是否符合预期，再执行
   `bun tools/agent-loop.ts --update-golden`。

5. **记录新版本**：`bun run sync:record`。
   记录新的提交号、文件散列与条目数；`bun run sync:update` 等价于先记录再提取。

6. **补齐游戏侧改动**：数据变化往往需要配套调整。
   新增怪物类别可能需要模型形状，新增物品类别可能需要使用效果，
   新增职业或种族需要检查角色创建界面的过滤逻辑。

7. **更新文档**：本页与 `README.md` 中的参考版本号，并在
   `docs/COGNITION.md` 的「参考事实」中记录结论。

## 实现说明

检测逻辑集中在 `tools/nethack-ref.ts`，被提取脚本、同步工具与 Agent 反馈循环共用。

判定优先使用文件系统，不启动子进程：

- 提交号与分支名直接解析 `.git/HEAD`、松散引用与 `packed-refs`。
- 关键文件用 sha256 前 16 位比对，条目数量用正则统计。

这样做的原因是实测数据：在本项目的运行环境里，一个进程内首次调用 git
需要约 10 秒（冷启动），之后每次约 0.1 秒。因此无漂移时 `sync:check`
只需约 0.3 秒；只有确认漂移、需要展示差异与提交列表时才调用 git，
此时约 6 秒。记录版本时也需要完整信息，属于一次性开销。

Agent 反馈循环以轻量模式集成该检查：报告中的 `reference` 字段给出
`up-to-date`、`drift` 或 `unavailable`，漂移时附加同步提示。
参考仓库不存在时静默降级，不影响游戏本身的回归检查。

## 常见情况

| 现象                     | 含义                 | 处理                                                    |
| ------------------------ | -------------------- | ------------------------------------------------------- |
| 提交号变化但关键文件未变 | 上游改动了无关文件   | 无需重新生成，执行 `bun run sync:record` 更新提交号即可 |
| 条目数量增加             | 上游新增怪物或物品   | 重新提取，补充翻译，检查模型与使用效果                  |
| 条目数量减少             | 上游移除或重命名条目 | 重新提取，清理引用旧 ID 的代码与翻译                    |
| 生成数据与记录不一致     | 提取脚本未重跑或失败 | 执行 `bun run extract` 后复查                           |
| 参考工作区不干净         | 本地有未提交改动     | 先提交或暂存，再记录版本                                |

## 边界

- 参考仓库不存在时 `sync:check` 直接报错退出，不影响其他命令；
  `bun run verify` 不依赖参考仓库。
- 记录只覆盖提取脚本读取的文件。若新增提取来源，需同步更新
  `REFERENCE_FILES` 与本节表格。
- 条目计数只作为漂移信号，正式数据以提取脚本输出为准。
